# Hangar: MVP Specification

## What we are building

Hangar is self-hosted deployment software that turns any spare computer into a personal Vercel. The target user has an old laptop or mini PC, installs a supported Linux distro on it, runs a single install command, and is done. From that point on they manage everything from a polished web dashboard called the Control Tower: they connect a GitHub repository, and every push to the chosen branch is automatically built, deployed, and served at its own subdomain with live build logs, deployment history, one-click rollback, environment variables, and basic resource monitoring. The entire product is judged on one thing above all else: how fast and painless it is to go from a freshly installed Linux box to a live app. Every design decision in this MVP should favor fewer moving parts, fewer questions asked of the user, and sensible defaults over configurability. Security hardening, multi-user support, and advanced features come later, but the architecture should not paint us into a corner on any of them.

## Brand voice and the aviation theme

Hangar has a playful aviation personality, in the same spirit as Homebrew "pouring" bottles and "tapping" casks. The theme should make the product feel memorable and fun without ever making it confusing. The guiding rule is **theme the copy, not the code**. Everything in the codebase uses plain, conventional engineering names: projects, deployments, statuses like `queued` and `failed`, tables, functions, and API routes are all named exactly as they would be in any other project, so contributors and Claude Code never have to decode a metaphor. The aviation wording lives only in user-facing text, and all of it is centralized in a single copy module at `packages/shared/src/copy.ts` (consumed by the dashboard) and in the installer's message strings, so the voice is consistent, easy to tune, and trivially reversible if a phrase turns out to be confusing.

The themed vocabulary for the MVP is as follows. The dashboard is the **Control Tower**, and it is served at the `tower` subdomain. The first-run setup wizard is the **Preflight Checklist**, and the one-time setup code printed by the installer is called the **boarding pass**. The sample app offered during onboarding is the user's **test flight**. Build logs are shown in the **Flight Recorder**, and the live runtime logs of a running app are shown under **Radio**. The host CPU, RAM, and disk readouts on the home page are the **Instruments** panel. Updating Hangar is **maintenance** and uninstalling it is **decommissioning**. Turning on public access through Cloudflare Tunnel is **opening the runway**. A commit's short SHA is displayed with the label **tail number** on deployment rows. Deployment statuses keep their plain enum values in code but display these labels in the UI: `queued` shows as **Holding**, `building` as **Preflight**, `deploying` as **Taking off**, `ready` as **Airborne**, `failed` as **Grounded**, and `cancelled` as **Scrubbed**. Every themed status label must have a tooltip or subtitle with the plain meaning ("Building your app", "Build or health check failed"), because a first-time user should never have to guess what a word means.

The voice should be light and confident, and the puns should show up mostly in the moments where a little personality helps: installer progress, empty states, success messages, loading text, and the occasional 404. Good examples: the installer prints "Clearing the runway..." while checking prerequisites, "Fueling up Docker..." while installing Docker, "Rolling open the hangar doors..." while starting the stack, and ends with "Wheels up! Your hangar is ready." An empty project list says "Your hangar is empty. Let's roll something in." A first successful deploy says "Wheels up! Your app is airborne." Loading states can rotate through short lines like "Taxiing to the runway..." The 404 page says "This flight has already left the gate." To avoid overkill, follow these limits: never more than one pun in any single sentence or UI element, buttons and form labels stay plain and literal ("Deploy", "Rollback", "Save", "Delete project"), and **no puns at all** in error details, security warnings, destructive confirmations, the setup code instructions, or anything a user needs to read carefully to avoid a mistake. When an error happens, the headline can be themed ("Grounded") but the body must explain plainly what went wrong and how to fix it.

Visually, the logo is a simple, friendly mark of a small plane parked inside an open hangar, and it doubles as the favicon. The Control Tower can include tiny themed touches such as a subtle runway-light pulse on the status dot of an in-progress deploy, but motion should stay restrained and never slow the user down.

## Tech stack

The project is a TypeScript monorepo managed with pnpm workspaces. The frontend is Vue 3 with TypeScript, Vite, Vue Router, Pinia for state, and Tailwind CSS for styling. The backend is Node.js (current LTS) with TypeScript using Fastify. The database is PostgreSQL accessed through Drizzle ORM with versioned migrations that run automatically on startup. Background jobs use pg-boss so that Postgres doubles as the job queue and the user never has to run Redis. Docker is controlled programmatically through dockerode talking to the host Docker socket. Traefik is the reverse proxy and routes traffic to app containers based on Docker labels, so deploying a new container with the right labels is all it takes to give it a hostname, with no config reloads. Request and response shapes are defined once as Zod schemas in a shared package and imported by both the API and the frontend, so types never drift between the two. Use Vitest for unit tests and Playwright for end-to-end tests.

## Repository layout

The repo contains `apps/web` for the Vue Control Tower dashboard, `apps/server` for the Fastify API and the deployment worker, `packages/shared` for Zod schemas, shared types, constants such as deployment status enums, and the `copy.ts` module holding all user-facing themed text, `installer/` for the install, update, and uninstall shell scripts plus the production docker-compose file, and `fixtures/` for small sample apps (a static site, a Node/Express app, a Vite app, and a repo with its own Dockerfile) used in integration tests and as the test flight option during onboarding. The API and worker live in the same Node process for the MVP and are split into separate modules internally so they can become separate containers later without a rewrite. In production the server also serves the built Vue SPA as static files, which means the whole platform is just three containers.

## What runs on the user's server

After installation the server runs a Docker Compose stack located at `/opt/hangar` with exactly three platform containers: `hangar-core` (API, worker, and the dashboard SPA), `hangar-db` (Postgres with a named volume), and `hangar-proxy` (Traefik). The core container mounts `/var/run/docker.sock` so it can build images and manage app containers. All platform containers and all deployed app containers join a dedicated Docker network called `hangar` so Traefik can reach them. The dashboard itself is routed through Traefik as well. All secrets, including the Postgres password, the session secret, and the 32-byte key used to encrypt environment variables, are generated by the installer and written to `/opt/hangar/.env` with permissions restricted to root. The Docker images for Hangar are published to GitHub Container Registry for both linux/amd64 and linux/arm64 so the product works on old x86 laptops and on Raspberry Pi 4/5 class devices.

## The install experience

The user runs one command on their server, in the form `curl -fsSL https://get.hangar.sh | sudo bash` (the domain is a placeholder until one is registered; during development the script can be run directly from the repo). The script is written in bash, is idempotent so it is safe to run twice, and prints friendly, colored, step-by-step progress using the themed installer lines described in the brand section, with each themed line followed by a dimmed plain description of what is actually happening so the output stays informative. It first checks that it is running as root, that the OS is a supported distro (Ubuntu 22.04, Ubuntu 24.04, and Debian 12 for the MVP; anything else gets a clear message and an option to continue at their own risk), that the CPU architecture is amd64 or arm64, that there are at least 2 GB of RAM and 10 GB of free disk, and that ports 80 and 443 are free. If Docker is not installed it installs Docker Engine and the Compose plugin using Docker's official repository method and enables the service. It then creates `/opt/hangar`, generates secrets, writes the compose file and `.env`, pulls the images, starts the stack, and waits until the core container's health endpoint responds. Finally it detects the machine's primary LAN IP and prints a large, clear "Wheels up!" success message containing the Control Tower URL and the boarding pass (one-time setup code). The setup code is a random value stored hashed in the database and is required to create the first admin account, which prevents anyone else on the network from claiming the instance before the owner does. Also ship `hangar-update` (performs maintenance: pulls new images, runs migrations via core startup, restarts the stack, and keeps all data) and `hangar-uninstall` (decommissions the stack: stops and removes it, and asks before deleting volumes and app data). Installing these helper scripts to `/usr/local/bin` is part of the installer.

## Networking and hostnames

The MVP supports two access modes and must work with zero DNS configuration out of the box. In the default LAN mode, every app is given a hostname using the sslip.io wildcard DNS service, so an app named `blog` on a server at 192.168.1.50 is reachable at `blog.192-168-1-50.sslip.io` from any device on the home network, and the Control Tower is at `tower.192-168-1-50.sslip.io`. The name `tower` is reserved and cannot be used as a project name. This gives every app a real subdomain without the user touching DNS or a router. In LAN mode traffic is plain HTTP. The base domain is stored as a setting so that if the server's LAN IP changes the user can update it in one place and all routes are regenerated. In the optional public mode ("open the runway"), the user owns a domain on Cloudflare, creates a Cloudflare Tunnel in the Cloudflare dashboard, and pastes the tunnel token into Hangar's settings. Hangar then starts a `cloudflared` container on the `hangar` network that forwards the wildcard `*.theirdomain.com` to Traefik, Cloudflare handles HTTPS, and no ports need to be opened on the router. The settings page walks the user through the Cloudflare steps with clear, plainly worded instructions. In public mode the Control Tower stays LAN-only by default and is only exposed publicly if the user explicitly turns that on, because it controls the whole machine.

## Onboarding flow in the dashboard

The first time the user opens the Control Tower they see the Preflight Checklist, a short setup wizard. Step one asks for the boarding pass and creates the admin account with a username and password. Step two shows the detected access mode and base domain, lets them confirm or edit it, and offers the optional Cloudflare Tunnel setup with a skip button. Step three connects GitHub by having them paste a fine-grained personal access token with read access to contents and metadata, with a direct link to GitHub's token creation page and the exact permissions to select; public repositories work without any token. Step four offers a test flight, deploying a sample app from the fixtures so the user sees a successful deployment within the first few minutes, then drops them on the main dashboard. The wizard should feel fast and confident and should never show a raw error without a human-readable explanation and a suggested fix.

## Projects and deployments

A project represents one deployed application. Creating a project asks for a repository (a GitHub URL, or a pick from a searchable list of the user's repos if a token is connected), a branch defaulting to the repo's default branch, a project name that becomes the subdomain (validated as a DNS label, unique, and not a reserved name such as `tower`), an optional root directory for monorepos, and the internal port the app listens on, which defaults to 3000 and can also be auto-detected from the build output or Dockerfile `EXPOSE` when possible. Static sites need no port. A deployment is one attempt to build and run a specific commit of a project. Deployment status moves through `queued`, `building`, `deploying`, and then either `ready`, `failed`, or `cancelled`, displayed with the themed labels from the brand section. Only one deployment per project can be building at a time, a new push while one is queued supersedes the queued one, and the MVP runs one build at a time across the whole server to protect low-powered machines. Builds time out after 15 minutes.

## How a build and deploy works

The worker picks up a deployment job, marks it `building`, and does a shallow clone of the exact commit SHA into a temporary directory, using the stored token for private repos. If the repo (or the configured root directory) contains a Dockerfile, it is used directly. Otherwise the worker uses Railpack to detect the framework and produce an image automatically, which covers Node, Vite, Next.js, Python, Go, static sites, and more without the user writing a Dockerfile. The image is tagged `hangar/<project>:<short-sha>`. Every line of build output from both stdout and stderr is written to the `deployment_logs` table with a sequence number and timestamp and is simultaneously pushed to any connected dashboard clients viewing the Flight Recorder. Once the image is built the deployment moves to `deploying`. The worker starts a new container from the image on the `hangar` network with the project's decrypted environment variables, a restart policy of `unless-stopped`, a default memory limit of 512 MB that the user can change per project, and Traefik labels that route the project's hostname to the configured port. It then polls the container over HTTP on its port until it responds or 60 seconds pass. On success it switches routing to the new container, stops and removes the previous container for that project, and marks the deployment `ready`, which gives zero-downtime swaps. On failure it removes the new container, leaves the previous one serving traffic untouched, marks the deployment `failed`, and records a clear, plain-language reason. The temporary clone directory is always cleaned up. To control disk usage, after each successful deploy the worker keeps the five most recent images per project and removes older ones, and the dashboard shows total disk used by Hangar images.

## Triggering deployments

Every project can be redeployed manually from the dashboard. Automatic deploys on push work in two ways depending on access mode. In public mode, Hangar shows the user a webhook URL and secret to add to their GitHub repo settings (or creates the webhook automatically through the API if the token has permission), and incoming webhooks are verified with the HMAC SHA-256 signature before any job is queued. In LAN mode GitHub cannot reach the server, so Hangar polls the branch head of each project through the GitHub API every 60 seconds and queues a deployment whenever the commit SHA changes. Polling must respect GitHub rate limits and back off gracefully. The dashboard should make it clear which trigger mode each project is using.

## Rollback, environment variables, and runtime controls

Each project page shows its deployment history with tail number (short commit SHA), commit message, author, branch, status, duration, and time. Any previous `ready` deployment whose image still exists can be rolled back to with one click on a plainly labeled "Rollback" button, which runs the same deploy and health check flow using the existing image without rebuilding. Environment variables are managed per project in a simple key and value editor, values are encrypted at rest with AES-256-GCM using the key from the server `.env`, values are masked in the UI by default with a reveal toggle, and changes take effect on the next deploy, which the UI offers to trigger immediately. Each project also has start, stop, and restart controls for its running container, the Radio view of the container's live runtime logs (separate from build logs), and a danger zone to delete the project, which removes its containers, images, and records after typed confirmation. The danger zone uses plain wording only.

## Dashboard design and real-time updates

The Control Tower should look modern and premium, closer to Vercel or Railway than to a typical admin panel. It uses a dark theme by default with a light theme option, generous spacing, clear typography, subtle status color coding (gray Holding, cyan Preflight, magenta Taking off, green Airborne, red Grounded, after the colors of cockpit flight displays), and smooth but restrained transitions. The home page shows a departures board with one row per project: name, live URL, last deployment, recent results, memory use, and current status. The Instruments strip at the top shows the host's CPU, RAM, disk, temperature, battery, and uptime, plus the machine's details and the Hangar version. The Flight Recorder log viewer is the centerpiece: a terminal-styled panel that renders ANSI colors, auto-scrolls while a build runs, pauses auto-scroll when the user scrolls up, and supports copying and downloading logs. Real-time updates use Server-Sent Events rather than WebSockets because all live data flows from server to browser; there is one SSE stream for deployment status changes and one per deployment for log lines, and reconnecting clients resume from the last sequence number they received so no lines are lost. Container metrics come from the Docker stats API, sampled every 5 seconds while someone is viewing them, and host metrics come from reading `/proc` inside the core container with the necessary host mounts. The layout must work on a phone, since users will check deploys from their couch.

## Data model

The `users` table stores id, username, password hash (argon2id), and timestamps; there is exactly one user in the MVP but the table exists so multi-user support is an addition and not a migration nightmare. The `settings` table is a key and value store for things like base domain, access mode, the encrypted GitHub token, and the encrypted Cloudflare tunnel token. The `projects` table stores id, name, repo URL, branch, root directory, port, memory limit, trigger mode, webhook secret, last seen commit SHA for polling, and timestamps. The `deployments` table stores id, project id, commit SHA, commit message, commit author, status, failure reason, image tag, container id, trigger source (push, poll, manual, or rollback), and start and finish timestamps. The `deployment_logs` table stores deployment id, sequence number, stream, line, and timestamp, indexed on deployment id and sequence. The `env_vars` table stores project id, key, encrypted value, and IV, with a unique constraint on project id and key. Old build logs beyond the last 20 deployments per project are pruned automatically. None of these names are themed.

## Security baseline for the MVP

Even though security features come later, the MVP must not be careless. Passwords are hashed with argon2id. Sessions use signed, httpOnly, SameSite=Lax cookies, and all state-changing endpoints are protected against CSRF. Login is rate limited. All secrets at rest are encrypted with the instance key. Webhook signatures are always verified. The boarding pass setup code is single-use and expires after first account creation. All user input that reaches shell commands, Docker, or Traefik labels is strictly validated, and the worker never builds shell strings from user input; use argument arrays everywhere. The README must clearly and plainly state that Hangar builds and runs arbitrary code from connected repositories with access to the Docker socket, so it should only be pointed at repositories the owner trusts.

## Development environment and testing

A developer should be able to clone the repo, run `pnpm install` and `pnpm dev`, and get the Vue dev server with hot reload, the Fastify server with watch mode, and Postgres plus Traefik via a dev docker-compose file, all working against the developer's local Docker. Use sslip.io with 127.0.0.1 for local hostnames so routing behaves the same as production. Unit tests cover the shared schemas, the deployment state machine, encryption helpers, webhook signature verification, hostname generation including reserved names, and a check that every deployment status has both a themed label and a plain description in `copy.ts`. Integration tests run against real Docker and deploy each fixture app end to end, asserting the app responds at its hostname, that a failed health check leaves the previous version serving, and that rollback works. Playwright covers the Preflight Checklist, creating a project, watching a deploy succeed, and rolling back. The installer is tested in a clean Ubuntu 24.04 VM (Multipass is a good choice) as a manual checklist for the MVP, and later in CI. GitHub Actions should run lint, typecheck, unit tests, and integration tests on every push and should build and publish multi-arch images on tagged releases.

## Build order

Build in this order and get each stage working end to end before moving on. First, set up the monorepo, Postgres, Drizzle, the dev compose file, and Traefik, and prove routing works by manually running one container with labels and reaching it at an sslip.io hostname. Second, build the worker pipeline as a standalone function that clones, builds with Dockerfile or Railpack, runs, health checks, and swaps containers, triggered from a script and storing logs in the database, tested against every fixture. Third, build the API with auth, the boarding pass flow, project and deployment endpoints, env vars, the SSE streams, and the GitHub polling and webhook triggers. Fourth, create `copy.ts` and build the Vue Control Tower: Preflight Checklist, project grid, project detail page, Flight Recorder, Radio, deployment history with rollback, env var editor, settings, and Instruments. Fifth, write the production compose file, the install, update, and uninstall scripts with their themed output, and multi-arch image publishing, then test the full flow from a blank VM. Sixth, polish: empty states, error messages, loading states, the 404 page, mobile layout, the logo and favicon, and a README with a screenshot, a GIF of a deploy going airborne, and the one-line install command front and center.

## Definition of done for the MVP

The MVP is done when someone can take a blank machine running Ubuntu 24.04 or Debian 12, run the one-line installer, open the printed Control Tower URL from their laptop, complete the Preflight Checklist, connect a GitHub repo, and see their app airborne at its own subdomain in under ten minutes of total effort, and when every subsequent push to that branch redeploys automatically with live logs, a failed deploy never takes down the working version, any past deploy can be restored with one click, and a first-time user never encounters a themed word whose meaning is unclear.

## Explicitly out of scope for the MVP

Multiple users and teams, per-branch preview deployments, custom domains per project, automatic Let's Encrypt certificates outside of Cloudflare, managed databases as a service, build caching beyond Docker's own layer cache, GPU passthrough to apps, scheduled jobs, backups, notifications, a GitHub App via the manifest flow, a `hangar` CLI or desktop client that installs over SSH, and the security monitoring features planned for later versions. Keep the code structured so each of these can be added cleanly, but do not build them now.
